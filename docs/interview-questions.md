### 3. 这 23 张表建了几个外键？

【考点】是否真的设计过数据库。

**参考答案**：

> **25 个**。我特意用外键而不是靠应用层维护，因为应用层会忘。

## B 组：数据库与并发（8 题，你的主战场）

### 6. 点赞怎么实现的？并发下会不会出问题？

【考点】并发思维。**这题从软肋变成了最强项，一定要讲透。**

**参考答案**：

> **我原来的实现有问题，现在改掉了，我可以对比讲。**
>
> 原实现是"先查后写"：`SELECT` 判断 `(user_id, post_id)` 存不存在，
> 存在就 `DELETE`，不存在就 `INSERT`。问题是：用户双击、或两个请求同时到达时，
> **两个请求可能都查到"不存在"，然后都 INSERT**，赞数就变成 2。
> 而且原来的 `likes` 表没有唯一约束，数据库也不会拦住它。
>
> 现在有两层保护：
> **一是数据层**——`post_likes` 的主键是 `(user_id, post_id)` 复合键，
> 重复插入直接被拒绝。代码用 `INSERT IGNORE`（MySQL）/ `ON CONFLICT DO NOTHING`
> （SQLite），然后**根据影响行数判断是否真的新增了**：
>
> ```php
> $inserted = $database->execute($sql, [...]);
> if ($inserted === 0) { return false; }   // 已存在，不重复计数
> ```
>
> **二是计数列与插入放同一个事务**，所以不会出现"记录插了但计数没加"。
>
> 另外我还做了客户端防护——按钮请求期间禁用。但那只是体验优化，
> **真正的保证在数据库**，因为客户端不可信。

### 8. 签到怎么防止重复领取？

【考点】幂等设计。**这是高光，讲透。**

**参考答案**：

> 靠一张 `rate_limits` 表，复合主键 `(user_id, action, window_date)`。
> 流程是：
>
> ```php
> if (!$this->limits->attempt($userId, 'checkin', $this->today(), 1)) {
>     return ['ok' => false, 'message' => '今日补给已领取'];
> }
> ```
>
> `attempt()` 内部是**先占位再判断**：用一条 upsert 原子地把计数 `+1`
> 并读回新值，如果超过上限就把这次占位**还回去**并返回 false。
>
> 为什么不是"先查再插"？因为那样两个并发请求可能都读到 0，
> 都认为可以领。先占位再判断的话，**决定胜负的是那一条原子语句**，
> 只有一个请求能拿到 1。
>
> 然后奖励发放和状态更新包在同一个事务里，
> 所以不会出现"加了钱但状态没置位"（用户能重复领）或
> "置了位但钱没加"（用户白丢奖励）。

⚠️ **主动说出残留问题会加分**：
> 严格说还有一个理论窗口：如果占位成功、但事务在提交前进程被杀，
> 那次占位不会回滚（因为 upsert 是独立语句）。彻底解决要把占位也放进同一个事务。
> 实际上因为这个操作很快，风险极低，但我知道边界在哪。

### 10. 评论奖励怎么防刷？

【考点】经济系统设计。**这题原实现是漏洞，现在是修复案例。**

**参考答案**：

> **原实现防不住，这是我修掉的一个真实漏洞。**
>
> 原来的逻辑是"发一条评论 +2 星尘"，**没有频率限制、没有字数下限**，
> 只校验内容不为空。所以用户写个"好"字重复提交就能无限刷星尘，
> 再把星尘换成装备——整个经济系统会被刷崩。
>
> 有意思的是，我**其他玩法都做了限流**（签到、掉落、抽奖都走每日限额），
> **唯独评论奖励漏了**。
>
> 修法是复用同一套限流：评论奖励也走 `rate_limits`，
> action 用 `comment_reward`，每天封顶 5 次，第 6 次正常发帖但不再给奖励。
> 我是用端到端测试验证的——连发 6 条评论，前 5 条返回 `awarded: true`，
> 第 6 条 `awarded: false`，余额冻结不再增长。
>
> 这个教训我记下来了：**做一个机制不等于做完了这件事，必须回头做一次
> "这个机制应该覆盖哪些地方"的普查。**

### 11. 抽奖的随机数用 `rand()` 有什么问题？

【考点】安全意识。

**参考答案**：

> `rand()` 不是密码学安全的，它基于线性同余，种子可推。
> 对纯娱乐的虚拟物品，实际危害有限，但**这是不该有的习惯**——
> 正确做法是 `random_int()`。
>
> 我在项目里有个对比：**CSRF token 我用的是 `random_bytes(32)`，是对的；
> 但抽奖和掉落最初用的是 `rand()`，是重构时漏掉的。** 现在全部统一成 `random_int()`。
>
> 另外抽奖还有个更实际的设计问题：**中奖概率原本硬编码在代码里**，
> 想调概率就得改代码重新部署。更好的做法是做成配置或数据表，
> 这样运营能自己调，也不用为改一个数字发版。

### 12. 购买物品怎么保证不超卖 / 不重复扣款？

【考点】事务与原子性。

**参考答案**：

> 三个检查 + 一个事务：
>
> ```php
> $item = $this->economy->findForSale($itemId);        // 商品在售
> if ($this->economy->ownsItem($userId, $itemId)) { ... }  // 未重复购买
> if (!$this->economy->debit($userId, $price)) { ... }     // 余额充足
> ```
>
> 关键是 `debit()` 的写法——**余额检查写在 SQL 的 WHERE 里，不是先查再减**：
>
> ```sql
> UPDATE user_profiles SET stardust = stardust - :amount
> WHERE user_id = :user_id AND stardust >= :amount
> ```
>
> 这样"检查"和"扣款"是**一条原子语句**，两个并发请求只有一个能成功
> （返回影响行数 1），另一个影响 0 行，被判定为余额不足。
> 如果用"先 SELECT 查余额，再 UPDATE 扣款"，两个请求可能都读到足够余额，
> 然后都扣——**余额变成负的，或者扣了两次**。
>
> 扣款和入库在同一个事务里，所以不会出现"扣了钱但没拿到物品"。
> 而且 `user_items` 的主键是 `(user_id, item_id)`，即使逻辑有漏洞，
> 数据库也不会让同一个物品重复入库。
>
> 另外余额列是 `UNSIGNED` **并且**带了 `CHECK (stardust >= 0)`——
> 双保险，因为 `UNSIGNED` 的行为依赖数据库配置（这点我踩过坑，下面第 14 题展开）。

### 13. 装备系统怎么保证"同类型只能穿一件"？

【考点】是否真的理解自己写的 SQL。

**参考答案**：

> 商品有 `type` 字段，分 `effect`（名字特效）、`avatar_frame`（头像框）、
> `badge`（徽章）。同一个 type 下只能装备一件。
>
> 实现是两步，包在一个事务里：
> 1. 一条 `UPDATE ... JOIN` 把该用户**所有同类型**的装备置 0
> 2. 再把目标物品置 1
>
> ```sql
> UPDATE user_items ui JOIN shop_items s ON s.id = ui.item_id
> SET ui.is_equipped = 0
> WHERE ui.user_id = :user_id AND s.type = :type
> ```
>
> 用一条 SQL 批量卸下同类装备，不用先查出来再循环 update。
>
> **这里我要主动说一个不足**：数据库层面没有强制"同类型只能一件"，
> 是靠应用逻辑 + 事务保证的。如果有人在事务外直接写库，是可以造出
> 两件同类都 equipped 的数据的。要彻底强制，需要用"函数索引"或者
> 一个只在 equipped 时存在的唯一键——MySQL 里可以靠生成列实现，
> 但我评估后觉得为了这个场景引入生成列不值得，所以选择了在仓储层
> 用事务保证，并且只允许通过这个入口修改。

## C 组：本项目的真实缺陷（8 题，**最能体现水平的一组**）

### 14. 你说发现了一个"静默数据损坏"，具体是什么？

【考点】排查能力、对基础设施的理解。**这是全场最独特的一题。**

**参考答案**：

> 我的余额列是 `INT UNSIGNED` 并带 `CHECK (stardust >= 0)`。
> 我写了个校验脚本，直接往真实 MariaDB 上跑约束探针，结果两条应该失败的没失败：
>
> ```
> UPDATE user_profiles SET stardust = -1 WHERE user_id = 9999;   -- 返回成功
> INSERT INTO users (...) VALUES ('probe', 'x', 'root', 'active'); -- 非法角色也成功
> ```
>
> 查了 `sql_mode`，XAMPP 捆绑的 MariaDB 是
> `NO_ZERO_IN_DATE,NO_ZERO_DATE,NO_ENGINE_SUBSTITUTION`——**缺少 `STRICT_TRANS_TABLES`**。
>
> 在非严格模式下，服务器会**静默修正**越界值而不是拒绝：写 `-1` 到 `UNSIGNED` 列，
> 实际存进去的是 `0`，只产生一条 **Warning**，应用完全看不到。
> 更关键的是：**`CHECK` 约束根本没被求值**，因为值在约束检查之前就已经被"修正"了。
> `ENUM` 同理，非法值被存成空字符串。
>
> **为什么我的测试没抓到**：我平时跑的是 SQLite，SQLite 永远拒绝这些值。
> **只有对真实引擎跑同一组探针才暴露。** 这是我印象最深的一点——
> 测试通过不等于正确，要问"我测的是不是和线上同一个引擎"。
>
> 修法是在连接层强制严格模式：
>
> ```php
> $pdo->exec("SET SESSION sql_mode = 'STRICT_TRANS_TABLES,NO_ZERO_IN_DATE,
>             NO_ZERO_DATE,ERROR_FOR_DIVISION_BY_ZERO,NO_ENGINE_SUBSTITUTION'");
> ```
>
> 修完后同一组探针 6 项全通过。我把这个脚本留在仓库里
> （`tools/verify-deployment.php`），当成验收的一部分。

### 15. 还有一个"时区混用"的问题，讲讲。

【考点】是否理解时间处理的坑。

**参考答案**：

> 起因是缓存过期和"最近一小时登录失败"这两个查询行为不对。
>
> 根因是**我在比较两个不同的时钟**：
> - SQLite 的 `CURRENT_TIMESTAMP` 返回的是 **UTC**
> - PHP 的 `date()` 用的是**应用时区**（`Asia/Shanghai`，UTC+8）
>
> 所以 `WHERE expires_at > CURRENT_TIMESTAMP` 这种写法差了 8 小时——
> 一条刚写好、1 小时后过期的缓存，会被判定为已经过期；反过来也可能永不失效。
>
> 而且还有第二个层面的问题：**我的命令行脚本没有设置应用时区**。
> 时区只在 HTTP 请求的内核里设置，所以 `bin/` 和 `tools/` 下的脚本用的是
> PHP 的默认时区——这台机器上是 `Europe/Berlin`。于是 Web 写的时间和 CLI
> 写的时间根本不在一个时区。
>
> 修法是把"比较用的时间"全部改成**在 PHP 里算好再绑定成参数**，
> 不再依赖数据库的 `CURRENT_TIMESTAMP` 做跨时钟比较：
>
> ```php
> 'SELECT payload FROM api_cache WHERE cache_key = :key AND expires_at > :now',
> ['key' => ..., 'now' => date('Y-m-d H:i:s')],
> ```
>

### 16. 你还发现了一个"平台相关的门禁 bug"，这是什么？

【考点】对工程质量的理解。**很少见，非常加分。**

**参考答案**：

> 我写了一个静态检查脚本（`tools/lint.php`），其中一条规则是
> "模板里输出变量必须经过转义函数"。
>
> 规则本身是这样判断"这个文件是不是模板"的：
>
> ```php
> str_starts_with($relative, 'templates/')
> ```
>
> 而 `$relative` 是这样算的：
>
> ```php
> $relative = str_replace($basePath . '/', '', $file);
> ```
>
> **在 Windows 上，路径分隔符是反斜杠**，所以 `$relative` 得到的是
> `templates\layout.php`——**那个前缀判断永远匹配不上，这条规则在 Windows 上
> 从来没运行过。**
>
> 结果就是最坏的一种情况：**在我写代码的机器上，它因为错误的原因"通过"了；
> 第一个诚实信号来自 CI——Linux 上规则正常执行，抓到 19 处，构建变红。**
>
> 修好后我逐个审阅那 19 处，发现**是规则太粗糙，不是模板写错了**。
> 绝大多数是这种：
>
> ```php
> class="action-btn <?= $hasLiked ? 'is-active' : '' ?>"
> ```
>
> 三元表达式的两个分支都是字符串字面量，不可能注入。如果把它们标成违规，
> **这条规则会因为噪音而被忽略，比没有规则更糟**。
>
> 所以我把规则改精确了：只有当表达式**可能产出不可信内容**时才报错，
> 并且每一种"放行"都在 `--verbose` 下列出来，不静默通过。
> 改精确之后剩下的 12 处是真该改的，我改掉了。
>
> 这件事让我对"门禁"有了新的理解：**一个只在特定平台上生效的检查，
> 比没有检查更危险，因为它给了你虚假的安全感。**

### 18. 你重构前那个版本最严重的问题是什么？

【考点】诊断能力。

**参考答案**：

> 我列几个，按严重度：
>
> 1. **CSRF 只覆盖了 2 个入口**。全站 7 个会改数据的入口里，只有发帖和删帖校验了
>    token，其余全都没有——包括**改密码**。
> 2. **私密笔记的删除用了 GET**。这个最危险：`secret_space.php?del=id`，
>    意味着我只要在论坛贴一张 `<img src="...secret_space.php?del=1">`，

> 这些在重构里都改掉了：CSRF 下沉到路由层统一强制、删除改 POST + token、

### 19. 旧数据迁移时遇到了什么麻烦？

【考点】真实工程经验。

### 20. 私密笔记的加密，密钥怎么管的？

【考点】安全边界意识。**一定要说清取舍。**

**参考答案**：

> 用 **AES-256-GCM**，密钥从 `APP_KEY` 经 HKDF-SHA256 派生，
> **密钥不在数据库里**。所以单纯导出数据库读不出内容。
> GCM 是带认证的加密，密文被改动会在解密时报错，而不是解出乱码。
> 每条消息用**新的随机 nonce**——GCM 下重用 nonce 会同时破坏机密性和完整性。
>
> **但我必须说清这个方案的边界**：
>
> 1. **它防的是"数据库泄露"，不防"主机被完全控制"**。密钥在环境变量里，
>    攻击者同时拿到 `APP_KEY` 和数据库就能全解。
> 2. **`APP_KEY` 丢失 = 所有笔记永久无法恢复**。这是刻意接受的代价——
>    因为不把密钥和数据放在一起，才能防住"备份泄露"。
> 3. 我**没有**做"连管理员也读不到"的设计（那种需要用户密码派生密钥，
>    代价是忘记密码就永久丢数据）。我评估后认为对这个项目不值得。
>
> 另外还有个实现细节：如果某条笔记解密失败（比如密钥轮换过），
> 我不会让它崩掉整个页面，而是**显示"此笔记无法解密"的占位**并记录日志——
> 用户需要知道那条笔记还存在，而不是静默消失。

### 24. 为什么从 mysqli 换成 PDO？

【考点】技术选型的判断力。

**参考答案**：

> 四个理由：
>
> 1. **具名占位符**。mysqli 只有位置占位符 `?`，参数一多就容易对错顺序；
>    PDO 可以写 `:user_id`，可读性和抗错性都更好。
> 2. **关闭预处理仿真**。PDO 默认可能用 PHP 侧转义来"仿真"预处理，
>    我把 `ATTR_EMULATE_PREPARES` 设为 false，让**驱动真正做预处理**。
> 3. **异常模式**。mysqli 手工检查返回值容易漏掉；PDO 设成
>    `ERRMODE_EXCEPTION` 后错误直接抛异常，不会静默失败。
> 4. **驱动抽象**。这一条在实际中真的用到了——我的测试跑在 SQLite 上，
>    生产跑 MySQL，同一套仓储代码两个引擎都能跑。
>    mysqli 只有 MySQL，做不到。
>
> 顺便说，第 4 条也带来了代价：**两个引擎的 SQL 有差异**。
> 比如 `INSERT IGNORE` 是 MySQL 专有的，SQLite 要用 `ON CONFLICT DO NOTHING`；
> `ON DUPLICATE KEY UPDATE` 也一样。我在仓储层按驱动分支处理，
> 这个差异本身也是测试帮我发现的（SQLite 下直接语法报错）。
> 还有一处我特意**不做兼容**：旧数据迁移器只支持 MySQL，因为它按定义
> 就是从旧 MySQL 读数据，我在类注释里写明了这一点。

## E 组：安全（5 题）

### 26. CSRF 是怎么做的？覆盖全了吗？

【考点】诚实度。**这题现在可以正面回答，但要讲演进。**

**参考答案**：

> **现在覆盖全了，但第一版没有——这个过程我讲一下。**
>
> 工具层一开始就是对的：32 字节随机 token 存 session，
> 用 `hash_equals()` 做恒定时间比较。问题是**只有发帖和删帖两个入口调用了它**，
> 其余五个写操作全漏了。
>
> 我判断这是"**做了机制但没有做普查**"的典型错误：每加一个功能，
> 只想着"这个功能要什么"，没想过"横切功能要覆盖哪些地方"。
>
> 修法是**把校验下沉到路由层**：所有非安全方法（POST/PUT/PATCH/DELETE）
> 在进入任何 handler 之前统一校验，token 可以从表单字段或 `X-CSRF-Token`
> 头取（因为 JSON 请求用头更方便）。这样**新加一个路由不可能漏掉**——
> 它不是靠开发者记得，是靠结构保证。
>
> 我还在登录和登出时**轮换 token**，防止权限变更前的 token 被重放。
> 加上 Cookie 的 `SameSite=Lax`，这是独立于 token 的第二层。

### 27. 会话安全怎么做的？

【考点】基础但重要的细节。

**参考答案**：

> Cookie 层面：`HttpOnly`（XSS 读不到 session id）、`SameSite`、
> `Secure`（HTTPS 环境下必须开，我做成配置项）。
>
> 会话本身：
> - **登录时轮换 session id** —— 防会话固定
> - **每 15 分钟再轮换一次** —— 限制被盗 id 的有效期
> - **2 小时空闲超时**
> - `use_strict_mode` 打开 —— 拒绝服务器没发过的 id
> - `use_only_cookies` —— 不接受 URL 里的 session id
>
> 还有一个实践问题我踩过：**session 文件默认写在系统的共享临时目录**，
> 而那个目录在共享主机上常常不可写。而且**不可写的时候
> `session_start()` 只报个 warning，请求继续执行**——结果是登录静默失效，
> 用户觉得"登录没反应"。所以我把会话目录收到项目自己的 `storage/sessions`，
> 不可写就明确报错而不是继续。

### 28. 上传功能的安全考虑？

【考点】是否真的想过攻击面。

**参考答案**：

> 我按顺序做了七层，其中**顺序本身也很重要**：
>
> 1. **传输层**：`$_FILES['x']['error']` 必须等于 `UPLOAD_ERR_OK`，
>    并对每种错误给出具体提示
> 2. **来源校验**：`is_uploaded_file()` —— 挡住伪造 `tmp_name` 指向
>    服务器任意文件（比如 `/etc/passwd`）
> 3. **大小限制**：在**解码之前**检查，因为解码才是吃内存的一步
> 4. **类型校验**：用 `getimagesize()` 读**文件内容**判断真实类型，
>    不看扩展名——所以把 PHP 脚本改名成 `.png` 会被拒绝
> 5. **像素数上限**：防"解压炸弹"——几十 KB 的压缩图可以解成几 GB 的位图
> 6. **重新编码**：统一转成 WebP，并**自己生成随机文件名**。
>    存下来的永远是我生成的图片，原始文件里的任何东西都过不去
> 7. **存放位置**：上传目录在文档根**之外**，通过前端控制器转发，
>    所以即使配置错了也不可能被当脚本执行
>
> **顺序为什么重要**：如果我先生成图片再检查大小，那就已经吃过一次内存了。
> 检查必须在昂贵操作之前。

### 29. XSS 怎么防的？

【考点】分层防御。

**参考答案**：

> 三层：
>
> **服务端**：模板输出统一走 `View::escape()`（内部是
> `htmlspecialchars(..., ENT_QUOTES | ENT_SUBSTITUTE, 'UTF-8')`），
> 而且**有静态检查强制**——没转义的输出会让构建失败。
>
> **客户端**：JS 构造 DOM 时用 `textContent` 和 `append`，
> **从不拼 HTML 字符串**。这样用户内容在实现方式上就没有被解析成标记的机会。
>
> **响应头**：所有 HTML 响应带 CSP，`script-src 'self'`——
> 即使某处漏了，内联脚本也执行不了。
>
> **需要特别处理的是 Markdown**：博客支持 Markdown，`marked` 会把 Markdown
> 转成 HTML，但 **`marked` 本身不做任何净化，而 Markdown 允许嵌原始 HTML**。
> 所以直接把 `marked` 的输出插进页面就是个 XSS 洞——一条
> `<img src=x onerror=...>` 就能执行。
> 我的渲染路径固定是 `marked` → **DOMPurify** → DOM，
> 中间那一步不能省。关闭 JS 时回退成纯文本显示。
>
> 还有一点：日志的原始 Markdown 我放在一个 JSON 编码的 `data-` 属性里传给
> 前端，而不是内联 script——**这样内容里出现 `</script>` 也逃不出那个元素**。

### 30. 假设我不小心把密钥提交到仓库了，你会怎么处理？

【考点】实际的安全响应流程。

**参考答案**：

> **第一，按"已泄露"处理，不管它看起来有没有被用过。** 因为 git 历史是永久的，
> `git rm` 删掉文件也没用，历史里还在，别人 clone 就能翻出来。
> 所以第一步永远是**吊销并轮换密钥**，不是清理仓库。
>
> **第二，轮换之后才考虑清理。** 清理有两种做法：
> `git filter-repo` 重写历史，或者干脆认为旧历史已污染。
> 但清理的优先级低于轮换——**因为密钥已经泄露了，清理只是减少后续风险**。
>
> **第三，堵住入口。** 改成只从环境变量读，并且**不保留任何硬编码回退值**。
> 我原来那个版本就有这个问题：`define('GITHUB_TOKEN', getenv(...) ?: 'ghp_真实值')`
> ——读不到环境变量就用硬编码值。表面上"支持环境变量"，
> 实际上密钥还在代码里。**没有回退值才是真的只用环境变量。**
>
> **第四，加自动检查。** GitHub 有 secret scanning，
> 也可以用 pre-commit 钩子扫描。
>
> 我实际就是这么做的：审计完整历史确认它**没有**进过仓库
> （`git log -S 'ghp_'` 零命中，那个配置文件从未被跟踪），
> 然后把它从代码里彻底移除。

⚠️ 这题的关键是**顺序**：先轮换，后清理。

### 31. 你项目里有哪些已知的安全边界 / 没做的事？

【考点】自我认知。**主动说边界比声称完美强得多。**

**参考答案**：

> 我列几个明确的：
>
> 1. **登录限流是数据库实现**，多实例部署时需要换成 Redis 这类共享存储，
>    否则每个实例各算各的次数。
> 2. **没有做二次验证（2FA）**，只有密码 + 登录失败锁定。
> 3. **私密笔记的密钥在环境变量里**，所以防的是数据库泄露，
>    不防主机被完全控制。
> 4. **没有 WAF / 速率限制在网关层**，只有应用层的按用户限流。
>    按 IP 的全局限流我只做了登录失败这一处。
> 5. **`basic` 的备份策略**：我有备份脚本，但没有自动化定时备份和恢复演练。
> 6. **限流表会持续增长**，我写了 `pruneBefore()` 但**没有接定时任务**，
>    所以目前要手动清理。
>
> 这些我都在 `docs/security.md` 里写下来了。
> **我认为知道自己系统的边界在哪，比声称它没有边界更专业。**

## F 组：测试与工程化（5 题）

### 32. 你的测试怎么组织的？为什么不全用 PHPUnit？

【考点】务实判断。

**参考答案**：

> 78 条单元断言 + 64 条模块校验，分两套：
>
> **单元套件**跑在 SQLite 内存库上，覆盖业务规则和安全逻辑——
> 签到幂等、评论奖励封顶、购买不重复扣款、余额不为负、
> 上传拒绝伪装的脚本、加密往返、点赞去重。
>
> **模块校验**跑在持久化的开发库上，覆盖各模块协作——
> 而且我特意让它**可重复执行**（每次都先清掉自己创建的数据），
> 这样它不是"只能跑一次"的脚本。
>
> **为什么不全用 PHPUnit**：这个项目刻意保持"无 Composer 依赖、
> `git clone` 就能跑"。我的测试框架只有 200 行左右，覆盖了断言、
> 异常断言、范围断言这些我真正需要的能力，而且**跑起来不需要装任何东西**。
> `composer.json` 里列了 PHPUnit 作为可选开发依赖，想用可以装。
>
> 我的判断是：**测试的价值在于"真的跑"和"跑得动"，不在于用了什么框架。**
> 当然，如果项目再大、需要 mock 和 fixtures，我会直接上 PHPUnit。

### 33. 测试怎么跑生产 schema？SQLite 和 MySQL 不一样啊。

【考点】对测试有效性的理解。**这题能暴露你是否真想过"测试测的是什么"。**

**参考答案**：

> 迁移文件是 **MySQL DDL**（生产目标），测试跑在 SQLite 上。
> 我的做法是写了一个**方言转换器**（`SqliteDialect`），在测试引导时
> 把 MySQL DDL 翻译成 SQLite 等价语句：
>
> - `AUTO_INCREMENT` → `INTEGER PRIMARY KEY AUTOINCREMENT`
> - `ENUM(...)` → `TEXT CHECK (列 IN (...))`
> - `UNSIGNED` 去掉、`ENGINE=`/`CHARSET=` 去掉
> - `KEY name (cols)` 这种内联索引 → 转成独立的 `CREATE INDEX`
>
> **为什么值得这么做**：测试里的 schema 和生产的**是同一份源文件**，
> 所以外键、唯一键、CHECK 约束在测试中**真的生效**。
> 我的"重复点赞被拒绝""孤儿行被外键拒绝"这些断言才有意义。
>
> **但我必须说这个方案的边界**，因为我在这上面栽过：
> 翻译不可能 100% 等价。**`UNSIGNED` 在 SQLite 里没有对应语义**，
> 所以 SQLite 根本不检查负数——这就是为什么
> "负余额被拒绝"这条断言在 SQLite 上是**因为我显式写了 CHECK 才通过**，
> 而在真实 MariaDB 上最初**是失败的**（严格模式问题，第 14 题）。
>
> 所以我现在**两套都跑**：SQLite 套件快速验证逻辑，
> 另有一个 `tools/verify-deployment.php` 专门对**真实引擎**跑约束探针。
> **测试通过不等于正确——要问"我测的是不是线上同一个引擎"。**

### 34. CI 是怎么配的？跑什么？

【考点】工程化实践。

**参考答案**：

> GitHub Actions，矩阵跑 **PHP 8.1 / 8.2 / 8.3**，每个版本四个步骤：
>
> 1. 全量语法检查（`php -l` 遍历所有 PHP 文件，并行 4 路）
> 2. 静态分析（`tools/lint.php`：分层边界 + SQL 插值 + 模板转义）
> 3. 测试套件
> 4. （可选）部署校验
>
> `fail-fast: false`，所以一个版本挂了不会掩盖其他版本的问题。
>
> **说个实际的教训**：我最初推送 CI 的时候**从没真正跑过它**，
> 结果三个版本全红。失败的是"静态分析"这一步——
> 因为我的检查脚本有个**平台 bug**（第 16 题）：
> 在 Windows 上路径分隔符是反斜杠，导致模板检查那条规则从来没生效过。
> **所以我本地"通过"是因为规则没跑，不是因为我代码干净。**
>
> 修好之后，CI 就变成我唯一信任的信号了。现在每次推之前我会本地跑
> 同样三步，但**我以 CI 的结果为准**——因为它是干净环境。

### 35. 你最想改但还没改的是什么？

【考点】技术债意识。**要具体，不要说"没什么可改的"。**

**参考答案**：

## G 组：综合与软技能（5 题）

### 36. 这个项目你最大的技术收获是什么？

**参考答案**：

> **"数据库层能表达的约束，就不要放在应用层。"**
>
> 我原来点赞、购买、签到全是"先查再写"，看着很直观，但在并发下必然失效,
> 而且失效方式很隐蔽——平时测不出来，只在真实并发下偶发。
> 把这些约束下沉到数据库之后（唯一键、外键、事务、`WHERE` 里带条件），
> **正确性不再依赖我记得在每处写检查**。
>
> 这个认知还延伸到别的地方：我把"限流"也做成了数据库里的一张表而不是内存计数，
> 因为内存计数在多实例下是错的。
>
> 第二个收获是**"测试通过 ≠ 正确"**。第 14 题那个严格模式问题，
> 我的测试全绿，但真实数据库上约束根本没生效。

### 37. 最大的失误是什么？

**参考答案**：

> **我做了一个安全机制，但没有做"覆盖性普查"。**
>
> 我写了 CSRF 工具、写了转义函数、写了每日限流表——**每一个单独看都是对的**。
> 但每一项都只覆盖了一部分入口：CSRF 覆盖 2/7、
> 限流覆盖了签到掉落抽奖却漏了评论奖励。
>
> 根源是我的思考方式是"这个功能要什么"，而不是
> "这个横切关注点应该覆盖哪些地方"。
>
> 我现在的做法是：**写完一个横切功能，立刻把全站所有同类入口列出来逐个打勾**，
> 而不是相信自己的记忆。更进一步，**能下沉到框架层就下沉**——
> 我的 CSRF 现在在路由层强制，所以"漏掉"在结构上不可能发生。
>
> **一个机制的价值不取决于它写得多好，取决于它覆盖得多全。**

### 38. 如果给你两周重做，你会怎么改？

【参考答案】**按优先级，并解释为什么这个顺序**：

> **第一优先，把已知的运维缺口补上（1–2 天）**：
> 限流表清理接 cron、备份自动化 + 恢复演练。
> 这些是"出事才后悔"的东西。
>
> **第二优先，真并发测试（2–3 天）**：起多个进程同时打同一个接口，
> 验证我说的那些约束在真并发下确实成立。
> 我现在的信心来自推理和探针，**我想把它变成来自测试**。
>
> **第三优先，性能收尾（2–3 天）**：清掉剩下的 `ORDER BY RAND()`、
> 列表查询加分页（现在有些地方是硬编码 `LIMIT`）。

> **第四优先，代码一致性（2–3 天）**：统一 API 响应格式与错误码，
> 把残留的旧风格代码收敛掉。
>
> **顺序理由**：**运维缺口的代价是"出事"，并发的代价是"数据错"，
> 性能的代价是"慢"，一致性的代价是"难维护"。**
> 前两个是正确性问题，后两个是体验和效率问题——不在一个量级。
